# Review Stage R2 — Stages 11.2–11.3 (GUI session/redock wiring + GUI session UX)

**Scope:** commits `309bc0b` (`feat(ui): wire GUI into continuing docking sessions
with redock confirm flow`, Stage 11.2) and `12c557c` (`feat(ui): add session
lifecycle controls, redock cancellation, and session log viewer`, Stage 11.3),
diffed against `c6a5d63` (the R1 fix commit), per `dev_plan.md` Phase 11. Runs
`/code-review` (correctness) and `/simplify` (reuse/simplification/efficiency/
altitude) per `development_process_rules.md` §4. This is the first review stage
to cover the GUI — the first externally-facing surface this phase changes — so
it specifically targets the three risks named in the plan's R2 entry: a stale
redock plan executing against changed params, Delete racing an in-progress
bridge, and whether destructive-action confirmation is really two clicks apart.

**Outcome:** 5 correctness findings, 10 quality findings
(reuse/simplification/efficiency/altitude). 10 fixed directly (commit follows
this report), 1 deferred with a written trigger, 4 accepted as documented
risk. All three of the plan's named risks turned out to be real, reachable
bugs (findings #1–#3 below) rather than the "confirmed fine" outcome a first
read of the existing guards (Delete's `running_here` check, the two-click
toggle-then-confirm pattern) would suggest — see each finding for the exact
reproduction. Full suite green after fixes: 708 passed / 14 skipped / 1
deselected, no regressions (`docker compose --profile dev run --rm
script-runner python -m pytest -m "not integration"`, up from 701 passed
before this review's fixes — +7 new tests for `missing_required_params` and
`rename_job`'s locking).

## Correctness (`/code-review`)

### 1. Detaching from an active bridge (New Session / Reset / sidebar Load) never checked whether it was still running
**Files:** `ui/app.py` (`render_parameters_panel`'s New Session/Reset buttons,
`_resume_session`), `ui/session_state.py::start_new_session`
**Triage: fixed immediately.**
`start_new_session()` and `_reset_session()` unconditionally discard
`st.session_state.bridge`/`job_id`/`interactive_session`, and `_resume_session()`
(sidebar **Load**) unconditionally reassigns `job_id`/`interactive_session` to a
different job — none of the three checked `bridge.is_running()` first. Reachable
sequence: start a docking session (or redock an existing one), then, while it's
still running, click **New Session** (enabled the whole time — its `disabled`
condition only checks `has_active_job()`, unrelated to whether that job is
running) or click **Load** on a different session in the sidebar (always
reachable — the sidebar renders independently of whatever the main panel is
doing). Both immediately (a) orphan the live background thread — nothing left
in `session_state` can observe or stop it, since `OrchestratorBridge` doesn't
track which `job_id` it's running — and (b) desync `st.session_state.job_id`
from the job the orphaned thread is actually writing into, which silently
defeats `_render_session_row`'s `running_here` check (`job["job_id"] ==
st.session_state.get("job_id")`) for that job. For a **redock** of an
already-completed session specifically, this reopens exactly the "zombie
directory" race Stage 11.3's own scope-addition note says it closed: the job's
stale pre-redock `workflow_results.json` still shows e.g. `status="failed"`
and now appears **deletable** in Session History while the orphaned thread is
still writing into that same directory. Fixed by adding
`_active_bridge_job_id()` (`ui/app.py`) — the one place "is this tab's bridge
running, and for which job_id" is computed — and using it to disable **New
Session** and **Reset** (with an explanatory `help=`) while true, and to
disable **every** sidebar **Load** button while true (loading any other
session while one is running would still cause the same desync). Delete's
existing `running_here` guard now also derives from this same helper instead
of its own inline check (folds in quality finding #7 below).

### 2. A staged redock plan survived a sidebar Load of a different session and could then execute against the wrong job
**File:** `ui/app.py` (`_handle_redock_request`, `_execute_confirmed_redock`,
`_resume_session`)
**Triage: fixed immediately.**
This is the exact "stale rerun plan" risk named in the plan's R2 entry, and it
is real: staging a redock (changing a parameter and clicking **Run Docking**
while a session is active) sets `st.session_state["_pending_rerun"]` to that
session's `steps`/`params`, and only the params-panel's **Confirm redock** /
**Cancel** buttons are gated on it — the *sidebar*'s **Load** button is not,
and `_resume_session()` (Load's handler) never cleared `_pending_rerun`.
Sequence: stage a redock for session A (no workflow has started yet at this
point — staging only computes a plan, per `_handle_redock_request`'s
docstring), then click **Load** on a different session B in the sidebar before
confirming. `interactive_session`/`job_id` now point at B, but the params
panel still shows **Confirm redock** describing A's old plan. Clicking it ran
`_execute_confirmed_redock()`, which used `session.job_id`/`session.state_manager`
(now B) together with `pending["steps"]`/`pending["params"]` (still A's) —
redocking session B's job directory with session A's unrelated parameters,
silently corrupting B's checkpoints/results. Fixed two ways: (1)
`_handle_redock_request` now tags the staged plan with the `job_id` it was
computed for; `_execute_confirmed_redock()` validates that tag against the
*current* active session's `job_id` before executing, discarding the plan with
an error instead of running it if they don't match; (2) `_resume_session()`
now also clears `_pending_rerun` directly, as defense in depth (matching what
`start_new_session()`/`_reset_session()` already did).

### 3. `rename_job()` writes `workflow_results.json` without the lock/atomicity the orchestrator's own write to the same file uses
**File:** `ui/job_history.py::rename_job()`
**Triage: fixed immediately.**
This is pre-existing code (predates Phase 11), but it became a live hazard
only once Stage 11.2 introduced a second, concurrent writer to an
already-completed job's `workflow_results.json` (a redock) — exactly the kind
of "fresh eyes on earlier-stage assumptions" this review stage exists to catch
(`development_process_rules.md` §4). `rename_job()` did a plain
`json.loads(...)` / `write_text(...)` with no locking, while the orchestrator's
merge-write to the same file (fixed for this exact class of bug in R1 finding
#1) uses `FileLock(job_dir / ".workflow_results.lock")` +
`atomic_write_json`. Unlike **Delete**, **Rename** has no `running_here` guard
either, so it stays clickable during an active redock. Sequence: redock an
existing session (orchestrator acquires the lock, reads, merges, is about to
write); rename that same session from the sidebar (unprotected read happens
against the pre-redock file, then writes back after the orchestrator's write
completes) — the rename's write clobbers the redock's freshly-merged results
with the stale pre-redock snapshot plus the new name. Fixed by making
`rename_job()` acquire the same `.workflow_results.lock` and use
`atomic_write_json`, so a concurrent rename now correctly waits rather than
races (verified by a new test that holds the lock on a background thread and
asserts `rename_job()` blocks until it's released). Rename intentionally keeps
no `running_here` disablement — the lock alone is sufficient to prevent data
loss, and disabling it too would block a legitimate "rename while it runs" use
case for no remaining correctness benefit.

### 4. `render_chat()`'s "failed" branch appended no chat message
**File:** `ui/app.py::render_chat()`
**Triage: fixed immediately.**
Of the four terminal-status branches in the completion-sync block
(completed / bridge-error / cancelled / `result.status == "failed"`), only
the last set `_job_done = True` with no `st.session_state.messages.append(...)`
— the common case for a workflow that catches its own exception internally
(`execute_workflow()`'s own try/except, which never lets an exception escape
to `OrchestratorBridge._run()`'s except block, so `bridge.get_error()` stays
`None`). The user saw nothing in the chat panel and had to separately check
the Results panel to learn the run failed. Fixed: the branch now appends
`"Workflow failed: {errors joined, or 'unknown error'}"`, matching the
existing `elif error:` branch's format.

### 5. Live-bridge error path in `_render_job_results()` skipped the Session Log viewer
**File:** `ui/app.py::_render_job_results()`
**Triage: fixed immediately.**
The `if error: st.error(...); return` branch (a bridge-level exception, as
opposed to an internally-caught workflow failure) returned without calling
`_render_job_log()`, unlike the completed/failed/cancelled branches a few
lines below it — so a user hitting a bridge-level exception couldn't expand
**Session Log** to see what happened before the crash, even though `job.log`
exists and would be shown for a plain workflow-level `"failed"`/`"cancelled"`
status. This was a direct symptom of quality finding #8 below (the two result
branches were maintained as separate copies); fixed together with it by
extracting one shared `_render_completed_or_failed()` helper that both the
live-bridge and disk-read paths call, so the two can no longer drift on what a
given status renders.

### 6. Required-param preflight loop duplicated between the GUI and the CLI
**Files:** `ui/app.py::_handle_redock_request` vs.
`nlp_orchestrator.py::_execute_partial_rerun`
**Triage: fixed immediately.**
Both independently iterated `REQUIRED_PARAMETERS_BY_STEP[step]` flagging
falsy values, verbatim except for cosmetic message text ("Cannot redock" vs.
"Cannot rerun") — exactly the class of drift `common/param_diff.py` was
already introduced in R1 to avoid, just not applied here. Extracted to
`rerun_planner.py::missing_required_params(steps, params)` (mirroring R1's
`changed_parameter_keys` extraction), used by both call sites now. 5 new unit
tests in `tests/test_rerun_planner.py`.

### 7. "Is this job running in this browser tab" computed ad hoc in multiple places
**Files:** `ui/app.py::_render_session_row`, `render_parameters_panel`
**Triage: fixed immediately** (folded into finding #1's fix). Centralized in
`_active_bridge_job_id()`, used by Delete's `running_here`, Load's disable
condition, and New Session/Reset's disable condition — a future change to
what "running" means only needs to change in one place.

### 8. `_render_job_results()` duplicated the completed/failed dispatch across its live-bridge and disk-read branches
**File:** `ui/app.py::_render_job_results()`
**Triage: fixed immediately** (this is what let correctness finding #5
happen — see that entry). Extracted `_render_completed_or_failed(result,
job_id, job_label, live=...)`, called from both branches.

### 9. `_handle_redock_request` reloaded from disk a value already held in memory
**File:** `ui/app.py::_handle_redock_request`
**Triage: fixed immediately.** `latest_params = session.state_manager.
load_latest_parameters() or {}` re-read the checkpoint file that had just been
written, one line earlier, from the identical in-memory `params` dict — a
redundant disk round trip on every redock click. Now reuses `params` directly.

### 10. Cancellation guard pasted identically onto all 5 step conditions in `execute_workflow()`
**File:** `services/llm_orchestrator/orchestrator.py::execute_workflow()`
**Triage: deferred, with trigger.** `"<step>" in services and not
_maybe_cancel()` is repeated verbatim at all 5 step-gating `if` statements,
the same duplication class R1 finding #11 already collapsed once for the
per-step `append_job_log()` calls in this exact function (via
`_log_step_done`). Real, and the risk is concrete: a future 6th workflow step
copy-pasted from an existing block without also copying `and not
_maybe_cancel()` would silently make Stop not apply to it, with nothing to
catch the omission. **Recommendation: worth doing eventually, not now** —
unlike the `_log_step_done` fix (a mechanical closure extraction), fixing this
properly means restructuring the whole ~300-line method into a step-list-driven
loop, since each step's body (not just its cancellation guard) is large and
distinct; that's a materially bigger, riskier change than a review pass should
make. Trigger placed: code comment at `orchestrator.py`'s `_maybe_cancel`
definition naming the symptom and the two conditions that should trigger
revisiting it (a 6th step is added, or the method is next restructured for an
unrelated reason), plus a matching Future Work bullet in `dev_plan.md`.

### 11. `_reset_session()` / `start_new_session()` remain two independently-maintained "clear session" paths
**Files:** `ui/app.py::_reset_session`, `ui/session_state.py::start_new_session`
**Triage: accepted as a documented risk.** `start_new_session()` must
enumerate every job-related key by name to stay consistent with what
`_reset_session()`'s wipe-everything-except-`preserve` clears; a new piece of
per-job state added later (as `_pending_rerun`/`interactive_session` were in
Stage 11.2/11.3) needs to be added to `start_new_session()`'s explicit list by
hand or the two silently diverge on what "starting fresh" means. Finding #1's
fix reduces the *danger* of that divergence (both call sites now get an
`is_running()` guard before they run at all) but doesn't remove the
duplication itself. **Recommendation: leave as-is** — consolidating two
call sites this different in shape (wipe-with-exceptions vs. explicit-clear)
into one mechanism is more restructuring than the current duplication
justifies; revisit if a third "clear some/all session state" path is ever
added.

### 12. `list_completed_jobs()`/`list_failed_jobs()` each independently scan the whole output tree; cache invalidation is coarser than the data that changed
**Files:** `ui/job_history.py::_scan_jobs`, `ui/app.py::_clear_all_job_caches`
**Triage: accepted as a documented risk.** The sidebar's two 15s-TTL caches
each do a full `glob` + JSON-parse of every `workflow_results.json` under
`orchestrator_output/` (doubled vs. before Stage 11.3 added the second list),
and renaming/deleting a session in either list clears *both* caches.
**Recommendation: leave as-is** — same reasoning as R1 finding #13 (the read
itself is what makes each list correct; there's no in-memory index to
maintain instead without a bigger change), and at current historical job
counts this isn't a measurable cost. Revisit if users report sidebar slowness
with a large number of historical sessions.

### 13. `_render_job_log()` re-reads and re-splits the entire `job.log` file on every rerun, uncached
**File:** `ui/app.py::_render_job_log()`
**Triage: accepted as a documented risk.** Every ~2s poll tick (and, once a
job is done, every unrelated Streamlit rerun) re-reads the whole file from
disk and calls `.splitlines()` on all of it just to keep the last 500 lines —
cost grows with total log size and elapsed job time, with no tail-read or
`st.cache_data(mtime)` optimization (unlike `_read_file_bytes` just above it
in the same module, which the function's own docstring contrasts itself
with). **Recommendation: leave as-is for now** — not measurable at today's
job.log sizes. Revisit if [[parallel_docking_future_work]]'s longer/larger
parallel-docking runs are observed to grow `job.log` into a range (many MB)
where this becomes noticeable, at which point a tail-read (seek from end)
is the right fix, not full-file caching (the file is actively appended to
while a job runs, which is exactly why it isn't cached today).

### 14. `InteractiveSession.has_active_job()`'s "active" state is implicit in two fields being truthy together
**File:** `services/llm_orchestrator/interactive_session.py`
**Triage: accepted as a documented risk.** `bool(self.job_id and
self.state_manager)` rather than an explicit `active: bool` field means code
that ever sets one of the two directly (bypassing `activate()`) would silently
report "not active" instead of erroring. **Recommendation: leave as-is** —
today only `activate()`/`clear()` touch these fields, both keeping them in
lockstep; not worth a field-level invariant for a mistake that hasn't
occurred. Revisit if a call site is ever added that needs to set one without
the other.

### 15. `WorkflowStateManager(...)` instantiated inline at two call sites
**File:** `ui/app.py` (`_handle_run_docking`, `_resume_session`)
**Triage: accepted as a documented risk.** Both are one-line, semantically
identical constructions today; no logic has diverged between them.
**Recommendation: leave as-is** — lower priority than the above, revisit only
if a third call site or added constructor logic makes the duplication
concrete rather than cosmetic.

## Exception-handling pass

Reviewed every `except` added or touched by this diff for the band-aid
pattern this file's own rules warn against (`development_process_rules.md`
§6: never catch broadly around business logic to silently continue or hide a
root cause; broad catches are legitimate only at real I/O/protocol
boundaries, converted into an explicit failure state). Two broad catches were
touched: `ui/orchestrator_bridge.py::OrchestratorBridge._run()`'s `except
Exception as exc: self._error = str(exc)` (a real thread/subprocess
boundary, converting any exception into a structured error the UI reads via
`get_error()` — legitimate) and the pre-existing, untouched
`orchestrator.py::execute_workflow()` top-level `except Exception as e` (already
reviewed in R1, unchanged behavior here). No new band-aid catches were
introduced by Stage 11.2 or 11.3.

Restating `development_process_rules.md` §0/§4 directly: this report reflects
